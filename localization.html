Where am I?

A vehicle with an IMU, a stereo camera and a map of landmarks, asking the oldest question in robotics. The answer is a maximum-a-posteriori estimate over every pose at once — and the only real knob is how many of those poses you are willing to solve for together. One is a Kalman filter. All of them is batch estimation. Below you can drag that knob and watch what it costs.

Lost in the Woods: the robot wanders among landmarks while the estimator tracks it. Twenty-one minutes of animation at sixteen times speed.

Turn the knob

The estimator below is the same one as the report, on the 2-D version of the problem: a robot with noisy odometry measuring range and bearing to known landmarks. Every pose in the window goes into one state, the whole thing is linearised, and one Gauss-Newton system is solved. Drag the window from 1 — which is exactly a Kalman filter — up to the whole trajectory.

The sandbox

Take the landmarks down to four and the estimate starts to look like the dead-reckoned path. Turn the blackout on and watch the error grow through it, then snap back when the landmarks return — the estimator is not tracking a position so much as tracking how sure it is.

One state, every pose

The trick that makes batch estimation batch is refusing to throw anything away. Instead of carrying a single current belief forward, you stack every pose from k₁ to k₂ into one enormous state vector and ask for the whole trajectory that best explains the whole dataset at once.

xk₁:k₂ = [ Tk₁, …, Tk₂ ]     Tk = Ξk Tk−1 = exp(Δtk ϖk) Tk−1

Poses live on SE(3), so the motion model is a matrix exponential rather than an addition and the errors are logarithms rather than differences:

ev,k(x) = ln( Ξk Tk−1 Tk−1 )∨     ey,kj(x) = ykj − (1/z) M Tcv Tk pj

Linearise both around an operating point, stack the Jacobians, and one sparse Gauss-Newton solve gives a correction to every pose simultaneously. The information matrix is block-tridiagonal with a fringe of landmark terms, and it is 6N × 6N — which is where the cost lives.

The sliding window is the same solve over a suffix of the trajectory, with the poses that fell off the back summarised as a prior. Shrink the window to a single step and every term but the newest disappears; what is left is an extended Kalman filter. The report puts it plainly: "when the window size equals 1, this practically becomes a Kalman Filter."

One more thing the report checks before any of this: whether the noise is actually zero-mean Gaussian. The IMU is — comfortably, and if anything the supplied covariance is under-confident. The stereo camera is not: vl and vr are tail-heavy with a −7 pixel bias. The estimator assumes it away, and it is worth knowing that it does.

What the window costs

Four seeds, 300 steps each, everything in scripts/tools/run_localization.py. The point of the sweep is not that batch wins — it does, and it should — but by how little, and at what price.

1

Batch is more accurate and cheaper

The report says smaller windows run faster, and per step that is exactly right — the information matrix is (6N)², so halving the window quarters the solve. But running a sliding window across a whole trajectory means doing that solve at every step. Batch does one solve, ever.

Over 300 steps: a window of 50 costs 9.4 s, a window of 1 costs 0.43 s, and full batch costs 0.53 s — cheaper than every window except the filter, and the most accurate of the lot. The sliding window earns its place because it runs online, not because it is cheap.

2

The window is not over-confident. The noise model is.

The report finds the sliding-window 3σ bounds fail to cover the error while the batch bounds are "perfectly bounded", and suspects a poor initial covariance estimate. That is testable, so I tested it: hold the true noise fixed and scale the covariance the estimator believes.

With the correct Q and R, a window of 10 puts 99.6 % of its errors inside its own 3σ — textbook. Tell it the noise is four times smaller than it is and that falls to 74.1 %. The position estimate does not move at all: 0.0338 m either way. A covariance mismatch does not make the estimate worse, it makes the estimate's own account of itself worse — which is more dangerous, because nothing downstream can tell.

Reproduce it

# NumPy and matplotlib only git clone https://github.com/thejerrycheng/localization-batch-estimation cd localization-batch-estimation python scripts/tools/run_localization.py --seeds 4 # four figures + results JSON

The sandbox runs assets/js/localization_engine.js — the same Gauss-Newton solve as scripts/tools/estimator.py, including the marginal covariance of the newest pose, which is what the 3σ readout uses. The SE(3) stereo-IMU version on the Starry Night dataset is in the report; the dataset is course-distributed and is not redistributed here.

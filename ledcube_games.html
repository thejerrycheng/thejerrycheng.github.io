The console ◆ 3-D Snake ◆ 3-D Pong ◆ 512 LEDs ◆ MIE438

Press start

Two games written for a display that is 8 cells wide, 8 deep and 8 tall, and that can only ever light one layer at a time. Snake gains a third axis and loses its walls — run off one face and you come back on the other. Pong gains a machine opponent that solves for where the ball will cross its own face and moves to meet it. Both run on the same multiplexed frame buffer the hardware uses.

Snake, without walls

Two things change when Snake moves into a volume, and only one of them is the obvious one.

The obvious one is the input space: four directions become six, and the two extra ones point along the axis you are looking down, so they are the two you cannot see yourself moving in. That is why the cube has to be draggable. On the hardware they are the shoulder buttons of the PS2 pad, for the same reason.

The one that actually changes the game is density. A 2-D 8 × 8 board is 64 cells and a snake of length 20 fills nearly a third of it; the 8 × 8 × 8 cube is 512, and the same snake fills 4 %. Self-collision stops being the pressure it is in two dimensions, and the difficulty moves entirely into navigation — finding a cell you cannot see because your own body is between it and your eye.

So the walls come off. Running off the +x face puts you back on −x, which removes the only remaining source of cheap deaths and leaves the game to be about the thing that is hard:

wrap(v) = ((v mod 8) + 8) mod 8  — applied per axis, every step

The double modulo is not decoration; JavaScript's % keeps the sign of its left operand, so -1 % 8 is -1, and a single modulo sends the snake to index −1 rather than to the far face.

The rest matches the hardware version: no straight reversal (the one input the PS2 build also refuses, because it is always a self-collision), grow by one on food, and food respawns only into a cell the body does not occupy.

The head has to blink

On a binary display the head and the body are the same brightness, so at any moment you cannot tell which end of a 20-cell curve you are steering. The fix that costs nothing is temporal: the head is toggled on and off at about 2 Hz, which is far below the refresh rate and therefore free — the multiplexer was going to redraw the frame anyway. It is the only per-LED "brightness" this display has, and it is spent on the one bit of state the player genuinely cannot infer.

The machine you are playing

The Pong opponent does not chase the ball. Chasing looks plausible and plays badly: the paddle is always behind, and against a fast ball it never arrives. Instead it does what a person does, which is to solve for where the ball will be when it gets there.

The ball travels in a straight line between bounces, so the time to reach the machine's face is exact:

t* = (7 − y) / vy   (only while vy > 0)

and the free-flight crossing point is x + vxt*, z + vzt*. The four side walls make that a guess rather than an answer, and the fix is to fold the coordinate rather than iterate the bounces — reflect it back into the box with a triangle wave of period 2(N−1), which is exact for any number of wall hits and costs one modulo:

fold(u) = u mod 2W,   then u > W ? 2W − u : u    (W = 7)

Then the paddle moves toward that point at a capped rate. That cap is the only thing that makes the machine beatable: the prediction itself is exact, so if the paddle could teleport there would be no game.

Aiming, and why it was necessary

The first version only defended, and against a competent player it produced rallies that never ended — both paddles arrived in time, every time, for minutes. A predictor that only defends cannot win; it can only fail to lose.

So the machine aims. Contact away from the paddle centre already imparts lateral velocity to the ball — that is what makes your own shots steerable — so the machine deliberately places its paddle off the intercept, on the side that throws the ball away from where your paddle currently is:

xtarget = fold(x + vxt*) − sgn(3.5 − xyou) · 0.9·skill

The offset has to stay inside the paddle's 1.5-cell half-width or the machine misses its own shot, which is a pleasing constraint: it can only aim as hard as it can still catch.

One slider, three effects

Skill does not degrade the prediction. A perfect predictor that merely moves slowly is beatable but never wrong, and reads as a machine asleep rather than one you out-thought. Skill instead moves three things at once: paddle rate 2.6 → 8.8 cells/s, aim error ±1.4 → 0 cells, and aim offset 0 → 0.9 cells. At the bottom it misjudges by most of a paddle width and you can pick a corner; at the top it is exact, and it is trying to make you run.

It is honest about the one thing it cannot do: while vy ≤ 0 the ball is travelling away and there is nothing to predict, so it holds its last intercept — the same hedge a human plays.

// fold a free-flight coordinate back into the box const fold = (u) => { const p = 2 * (N - 1); u = ((u % p) + p) % p; return u > N - 1 ? p - u : u; }; // where will it cross my face, and when const t = (N - 1 - this.p[1]) / this.v[1]; let tx = fold(this.p[0] + this.v[0] * t); let tz = fold(this.p[2] + this.v[2] * t); // aim: sit off-centre so contact throws the ball // away from where the human is standing const aim = 0.9 * skill; tx -= Math.sign(3.5 - this.pad[0] || 1) * aim; tz -= Math.sign(3.5 - this.pad[1] || 1) * aim; // move there, at the rate skill allows const rate = (2.6 + 6.2 * skill) * dt; const slop = (1 - skill) * 2.8;

That stand-in is a modelling choice, not a measurement of you — it exists so the slider could be calibrated to be monotone and to sit near even at the midpoint, which it does. Where you actually fall on it is the interesting part.

The paddle is 3 × 3 on an 8 × 8 face, so it covers 14 % of what it defends, and the ball speeds up 4 % per exchange to a cap of 18 cells/s — without that cap it eventually moves more than a cell per frame and passes through a paddle instead of hitting it.
